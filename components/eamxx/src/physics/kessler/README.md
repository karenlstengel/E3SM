# EAMxx Kessler Microphysics (Python/JAX)

The Kessler (1969) warm-rain microphysics scheme as an EAMxx atmosphere
process (`kessler`), with the physics in Python/JAX, called from EAMxx's C++
through EAMxx's embedded Python (pybind11). The JAX code is the LAFT
translation of the CCPP/CAM-SIMA Fortran scheme in
[ESCOMP/atmospheric_physics](https://github.com/ESCOMP/atmospheric_physics),
`schemes/kessler/kessler.F90` and `kessler_update.F90`
([NCAR/llm-fortran-modernization](https://github.com/NCAR/llm-fortran-modernization/tree/main/fortran2jax-kessler/_officialJAX),
`fortran2jax-kessler/_officialJAX`). The same JAX code runs on CPU and GPU.

The scheme has three moisture categories: water vapor (`qv`), cloud water
(`qc`, moves with the flow) and rain water (`qr`, falls relative to the
air). It does autoconversion, collection, evaporation and saturation
adjustment, plus rain sedimentation sub-cycled to satisfy the CFL condition.
References: Kessler (1969); Soong & Ogura (1973); Klemp & Wilhelmson (1978),
J. Atmos. Sci. 35, 1070-1096; Durran & Klemp (1983), Mon. Wea. Rev. 111,
2341-2361.

Other implementations of the same scheme live on other branches of this
fork, so they can be compared against this one:

| branch                | implementation                                                    |
|-----------------------|-------------------------------------------------------------------|
| `ren/kessler-claude`  | C++/Kokkos                                                        |
| `ren/kessler-bridge`  | the Fortran scheme called from EAMxx through a C++/Fortran bridge (`fortran_bridge/`) |
| `ren/kessler-JAX`     | this directory: Python/JAX                                        |

Performance results for this branch are in
`/glade/derecho/scratch/kstengel/GK_perf_utils/` (perf workflow and model
runs) and `GK_perf_utils/workflow/interactive/jax_driver_2026-10-29/RESULTS.md`
(the standalone driver: data movement, warmup, sub-cycle loop).

## The `kessler` atmosphere process

`KesslerMicrophysics` runs on the `physics` grid (the GLL dynamics grid for
this compset). Levels are top-down, as everywhere in EAMxx: index 0 is the
model top, `nlev-1` the surface.

Fields (the same as on the C++ branch):

| field | role | units | notes |
|-------|------|-------|-------|
| `T_mid` | updated | K | latent heating applied through `T_mid_tend` |
| `p_mid`, `pseudo_density` | required | Pa | |
| `qv`, `qc`, `qr`, `qi` (tracers) | updated | kg/kg | mixing ratios wrt dry air; `qi` is only checked, Kessler has no ice |
| `phis` | updated | m2/s2 | surface geopotential (0 for this compset) |
| `rho`, `dz`, `pk`, `theta` | computed | kg/m3, m, -, K | derived in pre-processing |
| `z_mid`, `z_int` | computed | m | heights above the surface |
| `precl` | computed | m/s | surface rain rate, averaged over the step |
| `relhum` | computed | % | |
| `T_mid_prev`, `T_mid_tend`, `st_energy` | computed | K, K/s, J/kg | `kessler_update` bookkeeping; `st_energy` is dry static energy |
| `vapor_flux`, `water_flux`, `ice_flux`, `heat_flux` | computed | | only when the energy fixer is on; set to 0 |

What `run_impl` does each call, in order (each step has an EAMxx timer
under `EAMxx::kessler::run::`):

1. `preprocess` (C++/Kokkos, on the device): `pk` = Exner function,
   `theta = T_mid / pk`, `dz` from `pseudo_density`, `rho =
   pseudo_density / (g * dz)`, then `z_int` and `z_mid` from `dz` (a
   team-level scan from the surface). One kernel, one team per column, as
   on the C++ branch; a `Kokkos::fence()` before the timer stops, so it
   measures the kernel and not only its launch.
2. Hand the fields to Python, depending on `kessler::py_backend` (see
   [Data paths](#data-paths-kesslerpy_backend)): `sync_to_host` of 14
   fields (`host`), or `py_pack`: copy the strided tracers into contiguous
   device copies (`device`).
3. `py_run`: `kessler.run(ncol, nlev, dt, lyr_surf=nlev, lyr_toa=1, rho,
   z_mid, pk, theta, qv, qc, qr, precl, relhum)`. Updates `theta`, `qv`,
   `qc`, `qr` and computes `precl` and `relhum`, in place.
4. `py_update`: `kessler.update(ncol, nlev, dt, z_mid, pk, theta, phis,
   T_mid, T_mid_prev, T_mid_tend, st_energy)`: the `kessler_update.F90`
   steps on the device, chained with no transfers between them:
   `timestep_init` (`T_mid_prev = T_mid`, `T_mid_tend = 0`), `update_run`
   (`T_mid_tend += (theta * pk - T_mid_prev) / dt`), apply the tendency
   (`T_mid = T_mid_prev + T_mid_tend * dt`; HOMME takes its forcing from
   the change in `T_mid` across physics, so without this the latent
   heating would be lost), `timestep_final` (`st_energy = cp * T_mid +
   g * z_mid + phis`).
5. Bring the results back: `sync_to_dev` of 12 fields (`host`), or
   `py_unpack`: copy the contiguous tracers back into the tracer field
   (`device`).

`lyr_surf`/`lyr_toa` are 1-based, as in the Fortran. Python returns nothing
to C++: every output is written into the arrays it was given.

`initialize_impl` calls, in order: `kessler.init(latvap, P0, rhoqr, gravit,
cpair, rair)` (constants from `scream::physics::Constants`; `init` stores
`pref = P0/100` in hPa, as the Fortran does), `set_backend(py_backend)`,
`set_run_variant(py_run_variant)`, and, when `kessler::py_warmup` is true,
`warmup(ncol, nlev, nlev, 1)` under the timer `kessler::init::py_warmup`.
`finalize_impl` calls `kessler.finalize()`, which writes the perf log.

Range checks registered in `initialize_impl` run as pre/postconditions on
every call: `T_mid` in [100, 500] K and `qv` in [1e-13, 0.2] (invariants);
`qc`, `qr`, `qi` in [0, 0.1] and `precl` >= 0 (postconditions). They can be
turned off with `kessler::enable_precondition_checks` /
`enable_postcondition_checks`.

## The Python side

### `kessler.py`

EAMxx imports `kessler.py` in the `AtmosphereProcess` constructor, from
`kessler::py_module_path`. At import it:

- sets `JAX_ENABLE_X64=1` (all physics is float64) and, if unset,
  `JAX_PLATFORMS=cpu`, before JAX is imported. GPU runs must set
  `JAX_PLATFORMS=cuda` in the run environment (`run.py` does);
- turns on JAX's persistent compilation cache, in
  `JAX_COMPILATION_CACHE_DIR` (default `.jax_cache/` next to `kessler.py`),
  for every compiled function regardless of size or compile time, so a
  second run with the same cache skips compilation;
- registers `jax.monitoring` listeners that log each compile stage (trace,
  lowering, XLA compile, cache read) to the perf log as `jax_monitor:*`.

It keeps the Fortran module variables as Python module state: `latvap`,
`pref`, `rhoqr` (`kessler`), `gravit` (`kessler_update`), `cpair`, `rair`,
and `errflg`/`errmsg`. They are passed into each bridge and taken back from
it ("INOUT pattern"; the bridges hold no hidden state). After the first call
they come back as JAX arrays instead of Python floats, which is one reason
`warmup()` calls everything twice.

`run()` calls `kessler_run` through its bridge and writes the six outputs
back into EAMxx's arrays. `update()` runs the four update steps on the
device and writes four outputs back. Both log per-step times to the perf
log (`kessler_run`, `writeback`, `kessler_update_*`, `kessler_apply_T_tend`).

### Bridges and `kessler_jax/`

`kessler_jax/` is the translation: one module per Fortran procedure, with a
jitted `*_core` function on JAX's `(nz, ncol)` layout. Each `bridge/*.py`
adapts one of them to EAMxx's `(ncol, nz)` arrays, with two entry points:

- `*_bridge` ("contract 1", host-facing): NumPy arrays in and out. Copies
  the inputs to the device unchanged, runs the device entry, and fetches
  every output in one batched `jax.device_get`.
- `*_bridge_device` ("contract 2", device-resident): the jitted function
  itself, JAX arrays already on the device in and out, no transfers. The
  `(ncol, nz)` <-> `(nz, ncol)` transposes happen inside the jitted region,
  where XLA fuses them into the kernels.

Integer arguments (`ncol`, `nz`, `lyr_surf`, `lyr_toa`, `errflg`) are static
for `jax.jit`: a new value compiles a new version.

`kessler.py` uses contract 1 for `kessler_run` with `py_backend=host` and
contract 2 everywhere else. `update()` always uses contract 2 for its four
steps: `kessler_update` does little arithmetic per value, and copying each
step's data to and from the device separately cost more than the Fortran
(measured 0.33x of serial Fortran), while chaining them on the device is
much faster.

### Data paths (`kessler::py_backend`)

How EAMxx's fields reach Python and come back:

- `host` (default): `run_impl` copies the 14 fields to host memory
  (`sync_to_host`), Python gets NumPy views of the host copies
  (`create_py_field<Host>`, no copy), `kessler.py` copies them to the device
  and back inside each call (on a GPU), and `run_impl` copies the 12 outputs
  back to the device (`sync_to_dev`). On a CPU build host and device are the
  same memory and the syncs return immediately.
- `device` (GPU builds; the same as `host` on CPU): no host copies.

How `device` works, and why:

- EAMxx passes NumPy arrays whose data pointers are device addresses
  (`create_py_field<Device>`). They carry only the pointer, shape and
  strides and must never be read as NumPy: that reads GPU memory on the
  host and segfaults (this is why `py_backend=device` used to crash).
  Upstream EAMxx works the same way and expects the Python module to
  re-wrap the pointer as a GPU array; its `cld_fraction_cupy.py` does it
  with cupy.
- `kessler.set_backend("device")` turns on the device path when JAX runs on
  a GPU. `run()` and `update()` then wrap each array in an object with a
  `__cuda_array_interface__`, which `jnp.asarray` imports on the GPU
  without a copy, call the contract-2 bridges, and copy the results back
  into EAMxx's arrays with device-to-device `cudaMemcpy` through `ctypes`
  (`libcudart.so.12` from JAX's CUDA plugin, so no cupy is needed), then
  wait for the copies.
- Those arrays must be contiguous, and `qv`/`qc`/`qr` are strided slices of
  the tracers field. So `initialize_impl` makes contiguous copies of them
  (`Field::clone`, kept in `m_py_contig`) and their device NumPy arrays
  (`m_py_contig_arrays`), and `run_impl` copies into them before the calls
  (`py_pack`) and back after (`py_unpack`), about 0.07 ms each at ne16.
  `finalize_impl` releases those arrays, because
  `AtmosphereProcess::finalize()` shuts down the Python interpreter right
  after it returns.
- On a CPU build device pointers are host pointers, and `kessler.py` uses
  the host path.

In the driver, `device` matches `host` bit for bit and takes 13.4e-3 vs
22.2e-3 s per call at ne16 and 0.101 vs 0.240 s at ne60 on one A100. Set
`XLA_PYTHON_CLIENT_PREALLOCATE=false` in the run environment for GPU runs
(`run.py` does), so JAX does not reserve 75% of the GPU next to Kokkos.

### Warmup and the JIT cache

Each jitted function compiles on its first call with a new signature, and
in the model that would land in the first time steps. With
`kessler::py_warmup=true`, `warmup()` compiles everything in
`kessler::init` instead. It calls `run()` and `update()` themselves on
dummy columns (no rain), twice, so each jitted function sees exactly the
arguments the model will give it, and the real calls hit JAX's in-memory
cache. (`jit(...).lower().compile()` would not fill that cache.)

`warmup()` runs after `set_backend()` and `set_run_variant()`, and on the
device path it passes its dummies the way EAMxx passes its fields (NumPy
arrays over `cudaMalloc`'d device copies), through the same import and
write-back. This matters: arrays imported from device pointers are
committed to the GPU, NumPy arrays given to `jnp.asarray` are not, and
`jit` compiles separately for each. Warmed with host arrays, the device
path recompiled all four bridges and `update()`'s `add`/`multiply` on the
first step and `kessler_run`/`timestep_final` again on the second (about
2.3 s at ne16, even with a warm persistent cache). The driver's
`--py-warmup --warmup 0 --per-call` prints the JIT cache misses of every
call; it should print 0 on both paths.

### The sub-cycle loop (`kessler_run`)

Almost all of `kessler_run`'s time is the rain sub-cycle. Each column needs
1 pass if it is dry and 17 to 144 if it is rainy (driver, synthetic
columns). `kessler_jax/kessler_run.py` runs each column's sub-cycle as a
`lax.while_loop` and `jax.vmap`s it over the columns. Under `vmap` JAX runs
one loop until the slowest column is done and masks the finished ones, so
every column does the slowest column's passes: 12x to 40x the necessary
work at 12% to 3% rainy columns. On the GPU each loop iteration also reads
the loop flag back on the host and launches several kernels. This is the
same problem the C++ branch had with its first, host-loop port.

`kessler_jax_experimental/` keeps `kessler_run_core`'s physics (copied
unchanged) and changes only how the loop runs; `kessler_jax/` is left as
translated, so the changes can go back to the LAFT translation as a clear
diff. `kessler::py_run_variant` selects one at run time (default
`current`, i.e. `kessler_jax` as translated), so one build covers all:

| variant | how the loop runs | for |
|---------|-------------------|-----|
| `current` | `vmap` of a per-column `while_loop` (`kessler_jax`) | default |
| `auto` | `pallas` on a GPU, `map` otherwise | recommended |
| `pallas` | one Pallas kernel, one program per column: the column's levels spread over the program's threads, its state in registers, its own number of passes, and no host round trip per pass. The C++ branch's team-per-column structure | GPU |
| `map` | `lax.map` over columns: each column runs its own loop, as the Fortran does (`do col` / `do while`) | CPU |
| `split` | one pass on all columns (dry columns finish there), then the vmapped loop only on the columns still running, gathered into a fixed-size buffer and scattered back | comparison |
| `split_map` | `split`, with `lax.map` on the gathered columns | comparison |
| `vmap` | the current structure rebuilt from the copied pieces | check |

Pallas on the A100 compiles through Triton (JAX 0.6.2). Triton cannot slice
values, so the level k+1 neighbour needed for sedimentation goes through
memory: store, `plgpu.debug_barrier()` (a `__syncthreads`), load one level
up, barrier. Blocks must be powers of two, so the 58 levels are padded to
64. float64 `exp`/`pow`/`sqrt` match XLA's bit for bit, and float64 `dot`
crashes Triton, so the kernel does not use it.

`kessler_run` alone, s/call, 8% rainy columns (driver):

| grid | current | split | map | pallas | C++ team-per-column |
|------|--------:|------:|----:|-------:|--------------------:|
| GPU ne16 | 10.9e-3 | 5.8e-3 | - | 1.5e-3 | 1.15e-3 |
| GPU ne60 | 97.9e-3 | 27.6e-3 | - | 7.4e-3 | 7.56e-3 |
| CPU ne16 | 33.9e-3 | 9.4e-3 | 3.4e-3 | - | 3.70e-3 |
| CPU ne60 | 0.511 | 0.138 | 48.6e-3 | - | 52.3e-3 |

Through `kessler.py`, all of `run` + `update` + data movement, ne16:

| s/call | current | split | map | pallas |
|--------|--------:|------:|----:|-------:|
| GPU, `py_backend=host` | 23.7e-3 | 18.9e-3 | - | 13.1e-3 |
| GPU, `py_backend=device` | 13.5e-3 | 9.7e-3 | - | 4.1e-3 |
| CPU | 36.2e-3 | 11.5e-3 | 5.7e-3 | - |

More detail, and how Pallas got there: `kessler_jax_experimental/README.md`.

## The Kessler compset

`F2000-SCREAMv1-KESSLER`
(`2000_SCREAM%KESSLER-noAero_SLND_SICE_SOCN_SROF_SGLC_SWAV`, in
`components/eamxx/cime_config/config_compsets.xml`): EAMxx with the HOMME
dycore and stub land, ice, ocean, river, glacier and wave components.
For `SCREAM%KESSLER`, `namelist_defaults_eamxx.xml` and
`config_component.xml` set:

- `physics` = `mac_aero_mic`, and `mac_aero_mic` = `kessler`: Kessler is the
  only physics. No radiation, turbulence or aerosols.
- `mac_aero_mic::number_of_subcycles`: Kessler calls per physics step. The
  default depends on the grid (e.g. 12 at ne30np4); the perf cases set 1
  or 4 with `atmchange`.
- No topography: `topography_filename` unset, `phis = 0`.
- Zero aerosol fields, and zero values for surface fields that EAMxx's
  surface exporter needs to exist (`precip_*_surf_mass`, `sfc_flux_*`).

The user-mods directory
`components/eamxx/cime_config/testdefs/testmods_dirs/eamxx/L58-kessler`
sets 58 levels in `SCREAM_CMAKE_OPTIONS` and aquaplanet-style coupler
settings (fixed orbit with zero eccentricity/obliquity, constant zenith
angle 42.05 deg, zero albedos).

Initial conditions are DCMIP2016 moist baroclinic wave states
(`FKESSLER_<grid>[_dayNN].cam.i.moist_baroclinic_wave_dcmip2016.nc`), set
with `atmchange initial_conditions::filename=...`. The derecho perf cases use
day-10 (raining) and day-1 (no rain) states from
`/glade/derecho/scratch/kstengel/inputdata/atm/scream/init/`. Other EAMxx
initial-condition files can be downloaded from
https://web.lcrc.anl.gov/public/e3sm/inputdata/atm/scream/init/.

## Building and running

### A case

The build needs EAMxx's Python support and a Python with JAX, NumPy and
pybind11. On derecho that is the conda env
`/glade/work/kstengel/conda-envs/jax-kessler` (JAX 0.6.2 with the CUDA 12
plugin); `jax-kessler-cpu` is a copy without the CUDA plugin, for runs with
`JAX_PLATFORMS=cpu`. From `cime/scripts`, with the env active:

```bash
module load conda && conda activate /glade/work/kstengel/conda-envs/jax-kessler
./create_newcase --case <case> --compset F2000-SCREAMv1-KESSLER --res ne16_ne16 \
    --machine derecho --compiler nvidia --project <project> \
    --user-mods-dir <E3SM>/components/eamxx/cime_config/testdefs/testmods_dirs/eamxx/L58-kessler
cd <case>
./xmlchange DEBUG=FALSE,NTASKS=128,NTHRDS=1,ROOTPE=0
./xmlchange --append SCREAM_CMAKE_OPTIONS='EAMXX_ENABLE_PYTHON ON'
./case.setup
./xmlchange CAM_TARGET=theta-l_kokkos
./case.build
```

For GPU, use `--compiler nvidiagpu` and, before `case.setup`:

```bash
./xmlchange NTASKS=4,NGPUS_PER_NODE=4,GPU_TYPE=a100
./xmlchange KOKKOS_GPU_OFFLOAD=TRUE,OPENACC_GPU_OFFLOAD=FALSE,OPENMP_GPU_OFFLOAD=FALSE,OVERSUBSCRIBE_GPU=FALSE
```

Before submitting, point the case at the Python module and set the run
environment (the conda env's `bin` on `PATH`, `JAX_PLATFORMS`, and for GPU
`XLA_PYTHON_CLIENT_PREALLOCATE=false`), e.g. in `env_mach_specific.xml`:

```bash
./atmchange kessler::py_module_path=<E3SM>/components/eamxx/src/physics/kessler
./atmchange kessler::py_warmup=true              # optional
./atmchange kessler::py_backend=device           # optional, GPU
./atmchange kessler::py_run_variant=auto         # optional
```

A JAX "gpucpu" run (HOMME on the GPUs, Kessler on the CPU) uses the GPU
build with `JAX_PLATFORMS=cpu`, `py_backend=host` and a variant that runs on
the CPU.

### Derecho perf workflow

The C++/Fortran/JAX performance comparison uses scripts outside this
repository, in `/glade/derecho/scratch/kstengel/GK_perf_utils/workflow/`
(see its README.md):

- `build.sh jax gpu` / `build.sh jax cpu` build from this checkout (the
  `jax` builds also serve `gpucpu` runs) into
  `e3sm_test/builds/jax_<hw>_<commit>[-dirty<hash>]/`, with
  `EAMXX_ENABLE_PYTHON ON` and the `jax-kessler` env, and freeze a copy of
  this directory in the build's `py_kessler/`, so later edits here do not
  change what older run cases import. Untracked files are copied too, but
  are not recorded in the build's `git_diff.patch`.
- `run.py` creates run cases that point at those builds and sets the
  environment above. JAX options: `--jax-cache compile|cache` (cold or warm
  persistent cache), `--jax-warmup`, `--jax-variant` (`py_run_variant`;
  adds `_jv<variant>` to the case name), `--py-backend` (adds `_pydev`),
  `--xla-flags`, `--jax-trace`.

### Standalone driver

`driver_kessler_py.cpp` calls `kessler.py` outside EAMxx, exactly as
`KesslerMicrophysics` does: EAMxx's `PySession` to start Python, Kokkos
"fields" laid out like EAMxx's (padded `(ncol, nlev)` views, `qv`/`qc`/`qr`
as strided slices of one tracers view), NumPy views built as
`create_py_field()` builds them, then `init`, `set_backend`,
`set_run_variant`, optionally `warmup`, and `run`/`update` with `run_impl`'s
arguments, on synthetic columns shaped like one rank of a production case.
It is not part of the CMake build; `build_driver_kessler_py.sh` compiles it
with the Kokkos/EKAT, flags, Python and pybind11 of an existing JAX case
build:

```bash
source <jax case>/case/.env_mach_specific.sh
module load conda && conda activate /glade/work/kstengel/conda-envs/jax-kessler
./build_driver_kessler_py.sh --case-build <builds>/jax_gpu/build --out ./driver_kessler_py_gpu
./driver_kessler_py_gpu --grid ne16-gpu --backend host,device,cai --warmup 3 --repeat 10
./driver_kessler_py_gpu --grid ne16-gpu --backend host,device --run-variant current,pallas,split --py-warmup --warmup 0
./driver_kessler_py_gpu --grid ne16-gpu --backend device --py-warmup --warmup 0 --per-call
./driver_kessler_py_gpu --grid ne16-gpu --rain-frac 0.08 --passes
./driver_kessler_py_gpu --grid ne16-gpu --variants auto,split,pallas
./driver_kessler_py_gpu --help
./check_kessler_py_bfb.sh --hw gpu        # or --hw cpu, with the CPU driver
```

- `--backend host,device,cai`: `host` and `device` are `run_impl`'s two
  data paths, timed per stage (`sync_to_host`/`py_pack`, `py_run`,
  `py_update`, `sync_to_dev`/`py_unpack`). `cai` (GPU only) bypasses
  `kessler.py`: `driver_kessler_cai.py` imports every field through
  `__cuda_array_interface__` and runs the contract-2 bridges, as a
  reference for the zero-copy path.
- `--run-variant LIST`: each backend once per `py_run_variant`, through
  `kessler.py`.
- `--nsteps N`: chain N calls, each from the previous call's output, as
  model steps do.
- `--py-warmup`, `--per-call`: `kessler.warmup()` as `initialize_impl`
  calls it, and the JIT cache misses of every call.
- `--passes`: the per-column sub-cycle pass counts of `kessler_run`
  (`driver_kessler_passes.py`, from a copy of `kessler_run_core` with a pass
  counter, checked bit for bit against the original), the work
  `vmap(while_loop)` does, and what a dry/rainy split would save.
- `--variants LIST`: `kessler_run` alone for each `kessler_jax_experimental`
  variant against the current one (`driver_kessler_variants.py`), times and
  bit-for-bit comparison.

Checks on every run: outputs bit for bit with the first run's, at every
step of a chain; later chains must repeat the first one bit for bit (a race
in a GPU kernel would show up here); every output finite and
`qv`/`qc`/`qr`/`precl` non-negative. The exit code is 0 only if all pass.
`check_kessler_py_bfb.sh --hw gpu|cpu` runs these over ne16/ne60, rain
fractions 0/0.03/0.08/0.12, every backend and every variant (GPU:
`current,vmap,split,pallas,auto` on host/device/cai; CPU:
`current,vmap,split,map,split_map,auto` on host/device), 3 chained steps
twice, and prints a pass/fail table.

The driver sets `JAX_PLATFORMS`, `XLA_PYTHON_CLIENT_PREALLOCATE=false` and
`KESSLER_PERF_LOG_PATH` (to `./driver_kessler_py_perf_log.csv`, in the
working directory) unless they are set. The embedded Python looks in the
working directory first, so run it from this directory or from one without
Python files of its own. Build and run on a compute node; an interactive
GPU job runs both the CPU and the GPU binary.

## Performance logging

GPTL (`EAMxx::kessler::*` timers) is only reachable from C++, so the Python
side logs its own timings with `kessler_perf_log.py`, under GPTL-style
labels (`a:EAMxx::kessler::run::py_run::<label>` for per-call steps,
`a_i:EAMxx::kessler::init::py_*` for one-time costs such as importing JAX,
starting the backend and warmup, and `jax_monitor:*` for compile stages).
Its import is optional (`try/except ImportError`), so removing it never
breaks the run.

`log_call()` and `log_event()` only update an in-process table of per-label
totals (guarded by a `threading.Lock`); there is no file I/O per call. (An
earlier version opened the CSV and took a cross-process `flock()` on every
call, which serialized every MPI rank against every other on every step.)
`flush_log()` runs once per rank, from `kessler.finalize()` /
`KesslerMicrophysics::finalize_impl()`: it appends this rank's totals to a
raw CSV (`KESSLER_PERF_LOG_PATH` with a `.raw` suffix) under one `flock()`,
then recomputes the summary over every rank that has flushed and rewrites
`KESSLER_PERF_LOG_PATH` with it, so that file always holds the final
summary:

```
label,count,walltotal_s,wallmax_s,wallmax_rank,wallmin_s,wallmin_rank,callmax_s,callmax_rank
```

- `count`, `walltotal_s`: calls and total time for that label, over all ranks
- `wallmax_s`/`wallmax_rank`, `wallmin_s`/`wallmin_rank`: the ranks with the
  highest and lowest total time, and their times
- `callmax_s`/`callmax_rank`: the single longest call, and its rank (this is
  where first-call compilation shows up)

Set `KESSLER_PERF_LOG_PATH` for every real run (`run.py` puts it in the
case directory); otherwise it falls back to `kessler_perf_log.csv` next to
`kessler_perf_log.py`. Both files are appended to, so remove old ones before
reusing a path. A rank that dies before `finalize_impl()` loses its
timings.

`kessler_perf_log.F90` is the Fortran version (same design, same CSV
schema, `O_APPEND` writes through `ISO_C_BINDING`). It is not compiled on
this branch; `ren/kessler-bridge` uses it.

#### Implementation notes

2. It seems like a good idea to create structs for passing input fields, output fields, and (if needed) parameters/etc. Note that this requires each member of the struct that is a field to be defined for both the C++ side (usually with `Pack` and Kokkos views) and the Fortran side (_unmanaged_ view of type `Real` in the same dimensions as the C++ version UNLESS WE ARE USING OPENACC THEN WE USE MANAGED VIEWS WITH `Real`???). 
3. You should create a transpose function for converting between the Fortran and C++ fields. See `transpose()` in the `packagename_functions.hpp` file. 
4. I _think_ you can only pass to Fortran the `get_field_out("fieldname").get_view<Pack**>().data()` object into the C to Fortran binding. 

#### Misc notes

Example OpenACC Fortran loop. Recall that it is more efficient to loop over `k` first in fortran 

```fortran
    !$acc parallel deviceptr(p_mid) 
    !$acc loop gang vector collapse(2) reduction(max:p_mid_max)
    do k = 1,pver
        do i = 1,ncol
            p_mid(i,k) = p_mid(i,k) * 2.0
        end do
    end do
    p_mid_max = MAXVAL(p_mid)
    !$acc end parallel
```
